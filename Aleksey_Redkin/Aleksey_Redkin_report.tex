\section{Введение}

Библиотека Spla\footnote{URL: \url{https://github.com/SparseLinearAlgebra/spla} (дата обращения:~30.09.2026).} предоставляет примитивы для работы с разреженными матрицами и векторами с ускорением на графических процессорах (GPU) различных производителей через открытый стандарт OpenCL\footnote{URL: \url{https://www.khronos.org/opencl/} (дата обращения:~14.10.2026).}. Графовые алгоритмы, включая поиск кратчайших путей из одной вершины (Single-Source Shortest Paths, SSSP), реализуются поверх этих примитивов. Объектом исследования выступает плата Milk-V Jupiter\footnote{URL: \url{https://milkv.io/jupiter} (дата обращения:~07.10.2026).} на базе открытой архитектуры системы команд RISC-V с GPU PowerVR (линейка графических процессоров компании Imagination Technologies)\footnote{URL: \url{https://www.imaginationtech.com/product/img-bxe-2-32/} (дата обращения:~07.10.2026).}.

\section{Постановка задачи}

На целевом устройстве алгоритм SSSP преждевременно завершал работу на отдельных графах: значения расстояний не обновлялись и оставались равными \texttt{FLT\_MAX} (максимальное конечное значение типа \texttt{float}~--- маркер недостижимости вершины), а сверка с эталонной реализацией на CPU (центральный процессор) показывала расхождение более чем в 99~\% вершин на графе \texttt{belgium\_osm}.

\textbf{Целью работы является} локализация причины отказа и разработка переносимого решения для её устранения.

Для достижения цели были поставлены следующие задачи:
\begin{itemize}
    \item локализовать место отказа в цепочке итераций алгоритма SSSP и установить его корневую причину на целевом устройстве;
    \item реализовать переносимое исправление;
    \item провести проверку исправления сверкой с эталоном на наборе тестовых графов.
\end{itemize}

Результаты работы необходимы пользователям вычислительной платформы RISC-V с GPU PowerVR, для которых библиотека Spla~--- инструмент решения графовых задач с аппаратным ускорением. В выполнении работы заинтересованы разработчики самой библиотеки.

\section{Описание предлагаемого решения}

Алгоритм SSSP в Spla выполняется итеративно, обновляя на каждом шаге фронт (множество активных вершин) с помощью вычислительных ядер OpenCL.

На проблемных тестовых графах в момент остановки фронт непуст, однако его буферы заполнены нулевыми байтами при сохранившемся с предыдущей итерации ненулевом значении счётчика размера фронта. Эффект воспроизводился в независимых запусках без отличий.

Такое поведение соответствует пропуску запуска вычислительного ядра и сохранению устаревшего значения счётчика из пула повторно используемых счётчиков библиотеки (пул не обнуляет счётчики при возврате). Незапущенным оказалось вычислительное ядро \texttt{reduce\_by\_key\_small} (свёртка пар \enquote{ключ~--- значение} с одинаковыми ключами) с одной рабочей группой (группой рабочих элементов OpenCL).

Если весь вход обрабатывается одной рабочей группой, её размер выбирается исходя из числа обрабатываемых элементов вплоть до общего максимума устройства (\texttt{CL\_DEVICE\_MAX\_WORK\_GROUP\_SIZE}), который на исследуемом GPU составляет 512~рабочих элементов. Однако у каждого скомпилированного ядра есть индивидуальный лимит (\texttt{CL\_KERNEL\_WORK\_GROUP\_SIZE}), запрашиваемый вызовом \texttt{clGetKernelWorkGroupInfo},~--- \foreignquote{english}{the maximum work-group size that can be used to execute the kernel} (максимальный размер рабочей группы, который может быть использован для запуска ядра)\footnote{URL: \url{https://manpages.debian.org/unstable/opencl-1.2-man-doc/clGetKernelWorkGroupInfo.3clc.en.html} (дата обращения:~30.09.2026).}. На исследуемом устройстве запрос возвращает для ядра \texttt{reduce\_by\_key\_small} лимит в 480~рабочих элементов. Проверка кода возврата при отладке показала, что при попытке запустить ядро с группой из 512~элементов драйвер отклоняет постановку в очередь с ошибкой \texttt{CL\_OUT\_OF\_RESOURCES} (недостаточно ресурсов для запуска).

Подобный отказ соответствует описанию в спецификации OpenCL~1.2 (версии языка, под которую собраны ядра): вызов с размером вплоть до максимума устройства формально допустим, а возврат ошибки \foreignquote{english}{\texttt{CL\_OUT\_OF\_RESOURCES} \dots\ because of insufficient resources \dots\ such as registers or local memory} (недостаточно ресурсов, таких как регистры или локальная память)\footnote{URL: \url{https://manpages.debian.org/unstable/opencl-1.2-man-doc/clEnqueueNDRangeKernel.3clc.en.html} (дата обращения:~30.09.2026).}~--- штатный ответ среды исполнения. Недочётом исходной реализации являлось отсутствие сверки размера запускаемых групп с индивидуальным лимитом ядра. Код возврата функции постановки ядра в очередь также не проверялся, поэтому программа считала запуск состоявшимся, а отказ драйвера выявлялся лишь внешней сверкой с эталоном.

Перед запуском вычислительных ядер с одной рабочей группой разработанное исправление сверяет размер группы с индивидуальным лимитом скомпилированного ядра. Проверяются ядро редукции \texttt{reduce\_by\_key\_small}, а также ядра \texttt{bitonic\_sort\_local} и \texttt{bitonic\_sort\_global} битонной сортировки~--- параллельного алгоритма упорядочивания пар \enquote{ключ~--- значение} по ключу. Вспомогательные функции добавлены в \texttt{cl\_program\_builder}~--- модуль сборки OpenCL-программ. В редукции при размере группы сверх лимита обработка направляется по существующему многогрупповому пути. В битонной сортировке запрашиваемые размеры групп ограничиваются сверху лимитом ядра. Решение не содержит аппаратно-зависимых констант и ветвлений по производителю: лимит запрашивается у драйвера.

Реализация решения осуществлялась с использованием языка C++17 и прикладного программного интерфейса OpenCL~1.2~C. Кросс-компиляция под архитектуру RISC-V~--- сборка исполняемых файлов для целевой платы на хосте (компьютере разработчика) с другой архитектурой~--- выполнялась с помощью набора инструментов Syntacore\footnote{URL: \url{https://syntacore.com/tools/development-tools} (дата обращения:~01.10.2026).}. Запуски проводились непосредственно на плате Milk-V Jupiter. Разработка велась в форке репозитория Spla\footnote{URL: \url{https://github.com/Redkin-Aleksey/spla} (дата обращения:~14.10.2026).}. Выявленный отказ зарегистрирован в системе отслеживания ошибок проекта как дефект\footnote{URL: \url{https://github.com/SparseLinearAlgebra/spla/issues/246} (дата обращения:~14.10.2026).}, а разработанное исправление предложено в виде запроса на слияние\footnote{URL: \url{https://github.com/SparseLinearAlgebra/spla/pull/247} (дата обращения:~14.10.2026).}, который на момент написания отчёта находится на рассмотрении у разработчиков проекта.

\section{Тестирование}

\textbf{Среда выполнения.} Тестовые запуски проводились на плате Milk-V Jupiter под управлением ОС~Bianbu~3.0.1 (Linux~6.6.63, riscv64): графический процессор \texttt{PowerVR B-Series BXE-2-32} (Imagination Technologies), драйвер версии~24.2@6603887, профиль \texttt{EMBEDDED\_PROFILE} (профиль OpenCL для встраиваемых систем), OpenCL~3.0. Ядра собраны с флагом \texttt{-cl-std=CL1.2}. За основу взята ветка \texttt{main} исходного репозитория Spla на коммите \texttt{b81d1e29}. Поскольку оценивается функциональная корректность, а не время выполнения, характеристики хоста на результаты вычислений не влияют: вычислительные ядра исполнялись на графическом процессоре платы, а независимая эталонная реализация~--- на её центральном процессоре. Хост использовался лишь для кросс-компиляции.

\textbf{Входные данные.} В запусках использовались симметризованные версии графов из набора graph-bench\footnote{URL: \url{https://github.com/SparseLinearAlgebra/graph-bench} (дата обращения:~30.09.2026).}~--- коллекции графов и скриптов запуска для тестирования графовых библиотек~--- с единичными весами рёбер: загрузчик матриц \texttt{MtxLoader} добавляет обратные рёбра, а пример \texttt{sssp} присваивает всем рёбрам вес~1,0. Исходные матрицы в формате Matrix Market (текстовый формат для разреженных матриц)\footnote{URL: \url{https://math.nist.gov/MatrixMarket/formats.html} (дата обращения:~10.10.2026).} взяты из открытой коллекции SuiteSparse Matrix Collection\footnote{URL: \url{https://sparse.tamu.edu} (дата обращения:~07.10.2026).}. Вычисляемые расстояния~--- числа с плавающей точкой одинарной точности. В таблице~\ref{tab:graphs} приведены характеристики загруженных (симметризованных) версий использованных графов~--- тех данных, которые непосредственно обрабатывал алгоритм. Значения округлены до 0,1~млн. Граф \texttt{amazon-2008} использован как контрольный граф, на котором отказ не воспроизводился, \texttt{belgium\_osm} и \texttt{roadNet-CA}~--- проблемные графы, на которых отказ наблюдался.

\textbf{Методика проверки.} Целью было проверить гипотезу о том, что ограничение размера запускаемых групп индивидуальным лимитом ядра обеспечивает совпадение результатов с эталоном. Программа \texttt{sssp} из репозитория Spla сверяет CPU- и GPU-варианты с независимым эталоном (последовательная реализация без OpenCL): строка \texttt{CHECK} отмечает проверяемый вариант, строки \texttt{VERIFY} перечисляют несовпавшие вершины. Отсутствие строк \texttt{VERIFY} при \texttt{CHECK acc} (проверке ускоренного варианта) означает совпадение с эталоном. Сравнивались исходная и исправленная версии на тех же графах. Модель вычислений детерминирована, поэтому результаты запусков воспроизводимы без статистического разброса и отдельная статистическая обработка не проводилась.

Результаты сопоставления с эталоном представлены в таблице~\ref{tab:verify}: столбцы \enquote{Расхождений до} и \enquote{Расхождений после}~--- число вершин, не совпавших с эталоном; столбец \enquote{Доля до, \%}~--- их доля от общего числа вершин графа.

До исправления первые расхождения на графе \texttt{belgium\_osm} имели вид \texttt{expected 465 actual 3.40282e+38} (ожидаемое расстояние при единичных весах~--- 465~рёбер; фактическое значение равно \texttt{FLT\_MAX}: вершины остались недостижимыми из-за преждевременного останова алгоритма). После исправления зафиксировано полное совпадение результатов на всех трёх графах: расхождений с эталоном нет.

Таким образом, на проверенных графах и конфигурациях детерминированный отказ вычислений устранён: предельный размер группы запрашивается у драйвера устройства, а корректность подтверждена совпадением с эталоном на всех тестовых графах.

\section{Заключение}

В ходе выполнения работы получены следующие результаты:
\begin{itemize}
    \item локализовано место отказа на плате Milk-V Jupiter и установлена его корневая причина: при индивидуальном лимите в 480~рабочих элементов ядро \texttt{reduce\_by\_key\_small} запускалось с группой из 512~элементов, а код возврата \texttt{CL\_OUT\_OF\_RESOURCES} не проверялся;
    \item реализовано переносимое исправление запуска одногрупповых ядер с учётом их индивидуального лимита;
    \item проведена проверка сверкой с эталоном: на всех тестовых графах расхождения полностью устранены.
\end{itemize}
